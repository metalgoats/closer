## 1. The three Copy buttons are dead, not just the CRM one

Gabriel, 2026-08-10: *"CRM Notes copy button not working."*

**He under-reported it.** Reading the code, all three are broken, and the cause is exact:

```js
// public/app.js:1471
document.querySelectorAll(".copy-btn[data-out]").forEach(btn => btn.addEventListener("click", async () => {
  const panel = btn.closest(".panel");                     // <- returns null
  const body  = panel.querySelector('[data-field="body"]').value;   // <- TypeError
```

Commit `3b4c93e` (*"Unify the debrief and outputs into one full-height section"*, TASK-106)
moved the Copy buttons **out** of each output's `.panel` and into the shared chip row
(`.subnav-actions` inside `.panel-subnav`). The handler still walks up looking for `.panel`.
There is no longer a `.panel` ancestor, so `closest()` returns null and the click throws
before anything reaches the clipboard. No toast, no error the user can see, nothing copied.

`#copyDebrief` still works, because it was deliberately built from the data rather than the
DOM — the comment above it at `app.js:1465` explains why, and it is the same reason this
broke.

**The fix is the same principle:** copy from `outs`, not from the DOM. Look the output up by
`btn.dataset.out` and read its current value from the textarea by `[data-out]` id, not by
tree position. Position-based lookups are what moved out from under this feature once already.

> ⚠️ **The test suite asserted this feature was fine.** `tests/ui-smoke.test.mjs:362` checks
> that *"all three copy buttons survive the title removal"* by counting three
> `class="copy-btn" data-out=` strings in the markup. All three were present the whole time.
> The markup was never the problem. **A test that counts buttons is not a test that they
> work** — this is the project's own "reading code is not verification" lesson, wearing a
> green check. Whatever replaces it must exercise the click path, not the HTML.

## 4. Two logins, because there is currently no way to have two

Named on the 08-11 call as *"separate logins and permission levels."* The real state is worse
than "they share an account":

- `users` (`migrations/0001_init.sql:3`) has **no role column**.
- The only route that creates a user is `POST /api/setup`, which **refuses once one user
  exists** (`index.js:621`). There is no signup, no invite, no admin user-management, and **no
  password-change route at all**.
- `requireUser` is called **once**, at `index.js:82`, purely as a gate. Nothing else in the
  API is scoped to a user. Every authenticated session sees every call, every account, every
  integration, and the Spend page.

So the shared credential is not laziness, it is the only thing the schema permits. The
minimum that makes two people real:

1. `role TEXT NOT NULL DEFAULT 'member'` on `users`, with `'admin'` for Ivan.
2. An admin-only `POST /api/users` to create a second login, and a self-serve password change.
   Keep `/api/setup` first-run-gated exactly as it is.
3. Decide, and write down, what a `member` cannot see. **Spend and Integrations are the
   obvious two** — the integrations route already goes to some trouble never to return a raw
   key, which tells you the intent was there before the users were.

> ⚠️ **This is not multi-tenancy.** TASK-027 is parked on purpose and it belongs to the pivot
> question, not to this round. Two named people on one account, with one of them unable to
> read the billing page, is the whole ask. Stop there.
